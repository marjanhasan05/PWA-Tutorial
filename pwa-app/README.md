# PWA App Notes

This project is a small React + TypeScript + Vite app used to learn the core pieces of a Progressive Web App.

## What We Built

This app now includes:

- a web app manifest for installability
- a service worker generated by `vite-plugin-pwa`
- offline-friendly caching for the app shell
- prompt-based service worker updates for safer production behavior
- a custom install prompt
- UI that keeps the main static design visible even when the network goes offline

## PWA Basics

A PWA is basically a normal web app plus a few extra pieces:

- a manifest so the app can be installed
- a service worker so assets can be cached and used offline
- a UI strategy that still feels good when the network disappears

The big idea is that your source files like `App.tsx` are not cached directly. The browser caches the built output generated from them, such as compiled JavaScript, CSS, `index.html`, icons, and the manifest.

## Project Files

[`vite.config.ts`](./vite.config.ts)

- Enables `vite-plugin-pwa`
- Defines the manifest
- Configures service worker generation
- Sets caching rules for page navigations and images
- Uses a prompt-based update strategy instead of forcing automatic reloads
- Enables PWA testing in local development

[`src/main.tsx`](./src/main.tsx)

- Boots the React app
- Registers the service worker with `registerSW`
- Prompts the user before activating a newly available version
- Logs when offline support is ready

[`src/App.tsx`](./src/App.tsx)

- Contains the main app-shell UI
- Uses the online/offline state
- Keeps the same design visible both online and offline
- Changes status text instead of replacing the page

[`src/hooks/useOnlineStatus.ts`](./src/hooks/useOnlineStatus.ts)

- Tracks browser network state
- Listens to `online` and `offline` events
- Returns a boolean that the UI can use

[`src/components/InstallPrompt.tsx`](./src/components/InstallPrompt.tsx)

- Listens for `beforeinstallprompt`
- Stores the event
- Shows a custom install button when the app becomes installable

[`src/vite-env.d.ts`](./src/vite-env.d.ts)

- Adds type support for Vite
- Adds type support for `vite-plugin-pwa`

[`public/`](./public)

- Holds static assets used by the app and manifest
- Contains icons that must exist for installability

## Important PWA Ideas

### 1. Source files are not cached directly

`App.tsx` itself is not what the browser caches in production.

The browser caches the built output created from your source files:

- `index.html`
- compiled JavaScript
- compiled CSS
- manifest
- icons
- images and other static assets

That is why offline support depends on the generated app shell, not on raw source files.

### 2. The service worker controls offline behavior

The service worker is what makes the app work offline.

In this project, `vite-plugin-pwa` generates it for us. We do not maintain a hand-written `sw.js`.

This project also uses a safer update flow: when a new service worker version is available, the user is prompted before the app reloads.

### 3. Offline UI should usually stay familiar

A better PWA experience is usually:

- keep the main design visible
- show a clear offline indicator
- only block or soften the parts that actually require the network

That is why this app now keeps the main layout visible even when offline.

## What You Need To Add PWA To An Existing Project

If you want to add PWA support to another project, this is the practical checklist:

1. Install a PWA tool.
   In a Vite app, `vite-plugin-pwa` is the easiest option.

2. Add a web app manifest.
   You usually need:
   - `name`
   - `short_name`
   - `theme_color`
   - `background_color`
   - `display`
   - `start_url`
   - icons

3. Register a service worker.
   Usually this happens in the app entry file like `main.tsx`.

4. Provide real icons.
   The manifest icon paths must point to actual files.

5. Define caching behavior.
   Decide how pages, JS, CSS, images, fonts, and API responses should behave offline.

6. Design the offline experience.
   Keep the app shell stable and communicate network state clearly.

7. Test it properly.
   Open the app online first, let the service worker install, then test offline behavior.

## Minimum Requirements For A PWA

At a practical level, a PWA usually needs:

- HTTPS in production
- a manifest
- a service worker
- installable icons
- an offline strategy

## How To Test This Project

### Local development

```bash
npm run dev
```

Open the app in Chrome or Edge on `http://localhost:5173`.

### Production-style testing

```bash
npm run build
npm run preview
```

This is the more realistic way to verify final PWA behavior.

### Offline testing flow

1. Open the app while online.
2. Wait for the service worker to register.
3. Refresh once so the cached app shell is definitely available.
4. Switch DevTools or your browser to offline mode.
5. Refresh again and verify that the main UI still loads.

### Offline testing flow in DevTools

1. Start the app with `npm run dev` or, for a more realistic check, `npm run build` and `npm run preview`.
2. Open the app in Chrome or Edge.
3. Open DevTools.
4. Go to the `Application` tab.
5. Open the `Service Workers` section and confirm a service worker is registered.
6. Open the `Manifest` section and confirm the manifest and icons are detected.
7. Reload the page once while still online so the app shell is cached.
8. Go to the `Network` tab.
9. Change throttling from `No throttling` to `Offline`.
10. Refresh the page.
11. Confirm that the main static UI still loads and that only network-dependent parts are limited.
12. Optionally return to the `Application` tab and inspect `Cache Storage` to see cached assets.

## Final Takeaway

The most important thing we learned is that a PWA is not just "make it installable."

A good PWA also:

- keeps the interface stable
- handles weak or missing connectivity gracefully
- uses caching intentionally
- communicates clearly to the user about what still works
